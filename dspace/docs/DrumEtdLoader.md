# DRUM ETD Loader

## Introduction

The DRUM ETD Loader is UMD custom functionality for processing files uploaded
from ProQuest into DRUM.

"ETD" stands for "electronic theses and dissertations".

## ETD Workflow

ProQuest periodically uploads Zip files to DRUM via SFTP to a specific
"incoming" directory for processing. ProQuest sends an email to
"<lib-drum@umd.edu>" with a list of the ETD files that were delivered
(or failed to deliver).

Each Zip file contains

* An XML file containing the metadata for the theses/dissertation
* One or more PDF files
* Occasionally, supplementary files such as research data, audio or video, or
  Graduate School forms. See
  "[Manual Review of ETD Packages](#manual-review-of-etd-packages)".

The "load-etd-nightly" cron job processes each Zip file in the "incoming"
directory, adding them to DRUM. Successfully processed Zip files are moved to a
"processed" directory so that they is not processed again.

Upon completion, the "load-etd-nightly" sends an email of the log messages
generated by the cron job.

If an error occurs when processing a Zip file, the Zip file will be "skipped"
and remain in the "incoming" directory, and will be processed again on the next
cron run.

## Manual Review of ETD Packages

A ProQuest Zip file normally contains exactly two files: the ProQuest
"_DATA.xml" metadata file, and the thesis PDF. Anything else in the package is
a "supplementary file", which the ETD Loader adds to the public "ORIGINAL"
bundle of the item, in the same way as the thesis itself.

Supplementary files have included Graduate School forms containing student
personal information, which should not have been published. As supplementary
files cannot be told apart from legitimate research data without looking at
them, packages containing them are routed to a person instead.

When the review workflow is enabled (see "drum.etdloader.review.enabled"), the
ETD Loader routes an item to the review workflow of the
"drum.etdloader.collection" collection if any of the following are true:

* the package contains a supplementary file
* the package contains more than one ProQuest-named PDF (the last one is the
  thesis; earlier ones are kept as supplementary files rather than being
  discarded)
* the package has no thesis PDF, or no ProQuest metadata file

All other packages, about 92% of a typical load cycle, are installed directly,
exactly as before.

For a routed item:

* Its supplementary files are restricted to the group given by
  "drum.etdloader.review.group". The thesis PDF keeps its normal access.
* Any embargo is applied before the workflow starts, rather than at
  installation, which does not happen for an item held in the workflow.
* Both sets of policies are "TYPE_CUSTOM", so that the collection's default
  (Anonymous) read policy is not added to those files when a reviewer approves
  the item.
* The reasons for the review are recorded in the item's
  "dc.description.provenance" metadata, which is hidden from non-administrators,
  and included in the ETD Loader log and email.
* The department collections are mapped by the
  "EtdDepartmentCollectionMappingAction" as the item leaves the workflow, since
  a workflow item cannot hold mapped collections.

### Prerequisites

The "drum.etdloader.collection" collection **must have workflow reviewers**
before the review workflow is enabled. DSpace archives a submission immediately
if no workflow step has any members, which would publish exactly the files that
need review. The ETD Loader checks for this: if the collection has no
reviewers, the item is skipped, an error is logged, and the Zip file stays in
the "incoming" directory to be retried on the next run.

### Notes for reviewers

A reviewer who decides that a restricted file is safe to publish can change its
access in the DSpace UI. Doing so does **not** update the extracted text and
thumbnail derivatives of the file, which are generated from it. Run

```bash
dspace filter-media -f -i <handle>
```

afterwards, so that the derivatives match the new access.

## ETD Loader Components

The ETD Loader functionality consists of:

* an SFTP server for receiving files from ProQuest
* The "load-etd-nightly"/"load-etd" scripts that loads the Zip files
* Java classes in the DSpace "additions" modules
* Angular components in the "umd-lib/dspace-angular" repository supporting
  the creation/editing/deletion of "ETD Departments".
* A special "dspace/config/log4j2-etdloader.xml" Log4J configuration for
  controlling the log format
* Configuration properties in "local.cfg"

## ETD Departments

----

**Note**: "ETD Departments" is the human-friendly GUI-based name -- the
Java and Angular source code uses "ETD Units".

----

The XML metadata provided by ProQuest includes one (or more) "DISS_inst_contact"
entries, for example:

```xml
<?xml version="1.0" encoding="ISO-8859-1"?>
<DISS_submission publishing_option="0" embargo_code="0" third_party_search="Y">
  ...
  <DISS_description ...>
    ...
    <DISS_institution>
      ...
      <DISS_inst_contact>English Language and Literature</DISS_inst_contact>
```

Each "DISS_inst_contact" must match an existing "ETD Department" in DRUM, which
is used to map the ETD into the appropriate DRUM collection.

Each ETD is also added to the DRUM collection specified in the
"drum.etdloader.collection" configuration property.

## ETD Loader Configuration Properties

The following properties are used to configure the ETD Loader.

### drum.etdloader.collection

The UUID of the collection that all ETD submissions are added to (in addition
to the collection specified in the "DISS_inst_contact" XML property).

### drum.etdloader.eperson

The email address of the DRUM EPerson used to load the ETD submissions.

### drum.etdloader.maxFileSize

Operational parameter that sets a limit (in bytes) on the size of files that
can be processed by the ETD Loader.

This parameter is necessary to prevent the ETD Loader from uncompressing a
Zip file entry that exceeds the resource limit of "drum-cron-ephemeral-vol"
ephemeral volume in Kubernetes (which would cause the pod to reboot).

If a Zip file contains an entry that exceeds the limit, the entire file will
be skipped, and a message added to the ETD log (and email).

This parameter is optional -- if not set (or set to "-1") no file size limit
will be enforced.

### drum.etdloader.review.enabled

Enables the manual review workflow described in
"[Manual Review of ETD Packages](#manual-review-of-etd-packages)". Defaults to
"false".

The "drum.etdloader.collection" collection must have workflow reviewers before
this is enabled.

### drum.etdloader.review.group

The name of the group that supplementary files of a routed item are restricted
to, while the item is being reviewed. Defaults to "Administrator".

### drum.mail.etd.recipient

Email address that receives the output message from the ETD Loader.

### drum.mail.duplicate_title

Email address that receives notifications of duplicate titles from the ETD
Loader.

## SFTP

A ProQuest-provided public key that is added to the SFTP configuration to enable
ProQuest to upload files.

See the "docs/Secrets.md" document in the "umd-lib/k8s-drum" repository.
